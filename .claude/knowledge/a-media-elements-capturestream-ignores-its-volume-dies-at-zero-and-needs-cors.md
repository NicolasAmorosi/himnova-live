## A media element's `captureStream()` copy ignores its volume, goes silent for good at volume 0 or muted, and needs `crossOrigin`
**Area:** projection / renderer / protocol
**Trigger:** touching `lib/level-tap.ts` (the audio strips' meters for Chromium's own elements), adding a `<video>`/`<audio>` that can sound, removing `crossOrigin="anonymous"` from one; a meter that reads nothing while the element plays, or `[level-tap] cannot measure` in the log

- **The copy is the sound BEFORE `element.volume`.** Measured 2026-11-15 (Electron 44, macOS) on a −12 dBFS 1 kHz WAV in the projector: an analyser on `captureStream()` read −12.0 at `volume` 1 and −12.0 at 0.5. A meter of what the room hears applies `20·log10(volume)` itself (`level-tap.ts`).
- **But volume 0 or `muted` silences the copy for good.** The same copy read `-Infinity` once the element was muted or set to 0, and STILL `-Infinity` after `muted = false` / `volume = 1`, with its track `readyState` "live" and the element still playing; a NEW `captureStream()` taken then read −12.0 at once. Stopping one copy's tracks does not affect another copy of the same element. So a tap is dropped the moment its element goes inaudible (`pause`/`volumechange` in the document's capture phase, not on the next 40 ms tick) and a fresh copy is taken when it sounds again. `LiveVideo` sets `muted` whenever its volume is 0, so LIVE's mute exercises this on every press (`audio-meters.spec.ts`, «again after a mute»).
- **A cross-origin element cannot be captured at all:** `SecurityError: Failed to execute 'captureStream' on 'HTMLMediaElement': Cannot capture from element with cross-origin data` (the pages are `file://` or the dev server, the media `worship://`). It needs `crossOrigin="anonymous"` on the element, and nothing on the server: Electron's `protocol.handle` path applies no CORS check to `worship://` (measured by a reviewer 2026-11-15: with `Access-Control-Allow-Origin` removed, such elements still load and capture, from `file://` and from the http dev server; without the attribute `captureStream()` throws). No header is sent. Range/206 seeking is unaffected (the media specs pass with it). Every media element carries the attribute, so none of them depends on how Chromium keys its shared media data (see [chromium-reuses-a-media-urls-data-across-elements-so-changed-bytes-need-a-changed-url.md](chromium-reuses-a-media-urls-data-across-elements-so-changed-bytes-need-a-changed-url.md)).
- **What works for the listening side:** `new AudioContext({ sinkId: { type: "none" } })` is accepted (its `sinkId` reads back as an `AudioSinkInfo`; the option is not in TypeScript's DOM types) and starts `running` without a gesture; `AnalyserNode`s fed from a `MediaStreamAudioSourceNode` and connected to nothing are processed. Never `createMediaElementSource`: it reroutes the element's sound through Web Audio, so `setSinkId` stops applying and a Web Audio failure silences the room. A captured video track copies every frame: stop it at once and keep only the audio track.
- Related: the engine's own meter is the filter's peak before mpv's volume, 230 ms ahead of the sound ([mpv-filter-metadata-is-last-frame-only-republished-on-ticks-and-runs-ahead-of-the-sound.md](mpv-filter-metadata-is-last-frame-only-republished-on-ticks-and-runs-ahead-of-the-sound.md)); main multiplies it by the session's linear volume (`media/audio-levels.ts`).
