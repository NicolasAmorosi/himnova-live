## A Playwright-driven soak measures DevTools' network buffer, not the app's memory
**Area:** projection
**Trigger:** a renderer's memory that climbs during a long E2E/soak run (projector, NDI window, control); `partition_alloc/partitions/buffer` growing with an `<unspecified>` owner in a memory-infra dump; deciding whether a «leak» is real

- Believed (2026-11-11/12, three investigations): the projector and NDI renderers leak ~1.5–1.8 MB/min through a service, in Chromium's Blink `buffer` partition (640 KB slots + 13.6/14.2 MB blocks, no dump provider claims them), plateauing near 190 MiB on the Mac and «without a ceiling» in 2 h on Windows. True: **Playwright enables the DevTools `Network` domain on every page it attaches to, and Chromium's `InspectorNetworkAgent` keeps each response body** (`InspectorNetworkAgent::DidReceiveData` → `NetworkResourcesData::ResourceData::AppendData` → `SegmentedBuffer::Append`, caught with `lldb` on `PartitionBucket::SlowPathAlloc` + Electron's Breakpad symbols). A 12 MB MP4 played by Chromium leaves a 13.6–14.2 MB copy; the «plateau» is most likely the agent's own buffer budget (inferred, not read in Chromium's source).
- The A/B that settles it (2026-11-12, Mac, the agents' exact loop, 6 laps): **driven without Playwright** (Electron started with only `--inspect` on main, everything done from main through `webContents.executeJavaScript` in the control window), the projector stayed at 191–197 MB and `buffer` at 4.1 → 4.2 MB; **with Playwright**, same app and loop, 222 → 354 MB and `buffer` 68 → 179 MB. Production has no DevTools session (the app's only `debugger.attach` is «Probar video», `Media` domain, detached at once).
- Confirmed on Windows over 4 h (2026-11-13, the packaged app, the same soak scenes and timings as the Playwright run that «leaked» +1.52 MB/min, driven from main instead): 83 laps, the projector's and NDI window's private memory floor went 68 → 66 and 66 → 64 MB between minute 30 and 235 (−0.002 and −0.004 MB/min), the control 123 → 113; lap-start values 243–245 MB from minute 9 to 236.
- Two traps on the way: a `SlowPathAlloc` breakpoint counts memory *requested*, not *kept* (the agent churned 139 MB in a short loop whose memory stayed flat), so confirm with memory-infra dumps; and a short loop of one big 4K + a tiny MP4 does not grow even under Playwright (inferred: the 4K's ranged bodies exceed the agent's per-resource limit and are dropped), so it takes mid-size files (the 12–20 MB barcode MP4s of the soaks) to pile up.
- Rule: **never judge renderer memory from a run Playwright drives.** Measure it with a driver that attaches no DevTools session to the windows being measured (main's Node inspector only), as `orig.mjs` and `soak-v2/herramientas/mem-soak.mjs` in the maintainer's plan folder `2026-11-11-memoria-y-arranque-ndi/` do. Frame, A/V and start measurements under Playwright are still valid.
- That driver's own trap (packaged app on Windows, 2026-11-12): the inspector's `require("electron")` resolves from the app's **working folder**, and started from the repo it found npm's `electron` package, which, without its binary, "installs" itself with `spawnSync(process.execPath, ["install.js"])`: inside the app that is the app itself, opened on the user's **real profile**, and main froze waiting for it. Start the app from a folder with no `node_modules` above it and check `require.resolve("electron") === "electron"` before using it.
