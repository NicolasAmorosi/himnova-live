## An audio output is named differently by Chromium and mpv on every system, and moving mpv to another one costs a reopen
**Area:** projection
**Trigger:** choosing an output per bus (PREVIEW/LIVE), matching a Chromium `audiooutput` to an engine device (`matchEngineDevice` in `src/main/media/engine-protocol.ts`), `device`/`setDevice` in `media-engine.ts`, or the NDI sound per device (`native/engine/ndi-audio-*`)

- **Names, measured 2026-11-15 (mpv's `audio-device-list` vs Electron 44's `enumerateDevices`):** macOS lists every device twice, `coreaudio/<UID>` and `avfoundation/<UID>`, and Chromium appends the transport to its label («MacBook Air Speakers (Built-in)», «ZoomAudioDevice (Virtual)», a USB device's «(vid:pid)»); one virtual device's base name even differs («Microsoft Teams Audio» vs «Microsoft Teams Audio Device»). Windows: `wasapi/{guid}` is only the LAST part of the endpoint id (mpv strips `{0.0.0.00000000}.`, so `IMMDeviceEnumerator::GetDevice` with it fails: enumerate and match the suffix), the description is the friendly name, plus `openal`. Linux (PipeWire): `pipewire/<sink>` AND `pulse/<sink>` with identical descriptions, plus a dozen `alsa/…` plugins; mpv 0.34 has no `pipewire/`. So a matcher filters to ONE prefix per system first, or every name is ambiguous.
- **A device mpv cannot open for one file's format:** given the file's own layout and format, macOS's ZoomAudioDevice refused a mono WAV and every AAC (mono, stereo, 5.1: planar float) with «unable to set the input channel layout … -50», while a stereo WAV played. The engine plays every file out as interleaved float stereo (`audio-channels=stereo`, `audio-format=float`, after the meter, which still reads the file's channels): all of them then play there, and on Windows and Linux too. mpv's upmix puts a mono file 3 dB down per side (-12 read -15.1 on the output); a 5.1 downmix is not normalized (a -12 tone on all six read -2 dBFS).
- **A device mpv cannot open at all** (macOS's «Microsoft Teams Audio») gave `engine-open` and dropped the audio track: an audio file ended, a video played silent, and `device auto` afterwards brought nothing back. Since 2026-11-15 the engine runs `audio-fallback-to-null=yes` (the file plays on, unheard, `current-ao` = «null») and says `{"ev":"audio-out","ok":false,"device":…}`, never an error; main's `EngineEvents.audioOut`.
- **An output unplugged while playing (measured 2026-11-15):** macOS moves the sound to the default output by itself and mpv never knows (`current-ao` stays «coreaudio»; the process played on the speakers ~1 s after an aggregate device was destroyed). Windows' audio service restarting leaves mpv on null with the device still listed. Only mpv's own `audio-device-list` (followed with hotplug on all three) tells the device is gone: the engine says `ok:false` when the named device leaves the list (~330 ms on macOS, ~10 ms on Linux) and reopens it by itself (`ao-reload`) when it is back; on null with the device listed it retries after 2 s, then 4, 8… up to 30 s (each try is a refresh seek). The same name sent again would change nothing in mpv: the engine reopens by hand while the output is lost.
- **Moving a playing engine (`device <name>`):** the old output goes quiet 1–23 ms after the command; the new one sounds after 24–311 ms (an audio file) or 243–448 ms (a video), by system; mpv's `avsync` comes back to 0 within ~1 s. **Moved while paused, mpv reopens the output only when sound flows:** play then sounds 244–556 ms late (2–18 ms with no move). A paused `seek` to where it stands right after the move reopens it before play: 8 ms (Windows), 12 ms (Linux), 222–228 ms (macOS). `takePreviewEngine`'s handover does that.
- **NDI per device:** a macOS stereo-mixdown tap hears the given processes on EVERY device (PREVIEW's headphones too), so the tap must be the device's (`initWithProcesses:andDeviceUID:withStream:`); a process tap ignores the system mute. The tap's aggregate device holds the tap ONLY: with the output device beside it as its clock (Apple's sample does that), a device that also has an input put that input first in the IOProc's buffers, and NDI carried it: ZoomAudioDevice (1 in, 1 out, a loopback) read -0.4 dBFS (another process's -3 tone plus ours) where the tap alone reads our -12. A tap re-created on a user aggregate device hears nothing (engine-7 too): test unplugs with it measure the capture's state, not its level. The capture is watched (`appAudioHealthy`): an IOProc silent for a second, a tapped device gone, the default moved under «auto», a failed WASAPI call, a Windows audio service with a new process id (its process loopback stays alive but deaf, no error) or a failed `pa_simple_read` restart it; off, it is tried every 2 s. PipeWire moves a `<sink>.monitor` stream to the default when the sink goes and back when it returns, with no error. Windows' endpoint loopback (used only with PREVIEW apart) carries that output's Windows volume (a -12 tone read -22.5 / -25.1 on two Steam virtual outputs; process loopback -12) and showed 9–10 ms timestamp gaps on those virtual outputs every few hundred ms, unchecked on a real one. Linux's `<sink>.monitor` works for `pulse/` and `pipewire/` names alike. Moving the capture at run time: 31 ms (Windows), 64 ms (Linux).
- **No answer is not «cannot choose»:** `devices()` gives null both for an engine-7 and for one that did not answer in time (a spare still starting, stopped, replaced at launch). Taken as engine-7, the control window put Chromium's files on the chosen output and the engine's (and the NDI capture) on the default with no warning (audit 2026-11-15, reproduced with SIGSTOP on the spare). `matchAudioOutputs` now answers `"none"` only when the engine said it is older, `"pending"` otherwise, and a pending bus stays whole on the default and is asked again every 2 s.
- **The first route at launch** reaches main 190–270 ms after the control window is usable (Mac, 2026-11-15): nearly all of it is Chromium's FIRST `enumerateDevices` in that window (250–300 ms); the engine's names cost ~1 ms by then. A warm-up `enumerateDevices()` at the effect's start did not shorten it (measured), so nothing cheap is left there.
